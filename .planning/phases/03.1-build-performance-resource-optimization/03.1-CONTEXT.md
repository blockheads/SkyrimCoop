# Phase 03.1: Build Performance & Resource Optimization - Context

**Gathered:** 2026-03-27
**Status:** Ready for planning

<domain>
## Phase Boundary

Reduce MinGW cross-compilation build times and resource usage to make iterative development practical. The current releasedbg build produces 2.4GB of static archives and takes 6+ minutes for a full rebuild, with the monolithic link step as the primary bottleneck. This phase optimizes the build pipeline without changing runtime behavior or feature scope.

</domain>

<decisions>
## Implementation Decisions

### Link Time Reduction
- **D-01:** Switch to **mold** as the linker for MinGW cross-compilation. Drop-in replacement for GNU ld, 5-10x faster on large inputs.
- **D-02:** Enable **split DWARF** (`-gsplit-dwarf`) to move debug info into separate `.dwo` files. This dramatically reduces archive sizes and link-time I/O — the main driver of the 2.4GB → 86MB gap between releasedbg and release.
- **D-03:** Convert **all internal libraries to shared DLLs** for the dev build pipeline. This includes STServer, SkyrimCoopNetworking, ESLoader, Console, SkyrimEncoding, and all other internal targets. Maximizes incremental link speed — changing one library only re-links that DLL, not the entire client.

### Compilation Speed
- **D-04:** Enable **ccache** for the MinGW cross-compilation toolchain. XMake has built-in ccache support. Massive speedup on rebuilds where only a few files change.
- **D-05:** Keep **unity build** enabled but tune the batchsize. Current batchsize=12 may be too large for iterative development (one file change recompiles the whole batch). Tune down for dev builds, keep high for CI/release builds.

### Build Mode Strategy
- **D-06:** Add a new **`devbuild` XMake mode** optimized for development iteration speed: `-O0` (no optimization), split DWARF, mold linker, shared internal libs. This is separate from `releasedbg` (which keeps `-O2` for realistic runtime testing). Developers use `devbuild` for edit-compile-test cycles and switch to `releasedbg` for runtime validation.

### Resource Management
- **D-07:** **Auto-detect available RAM/CPU** and cap parallel jobs accordingly. mold is inherently more memory-efficient than GNU ld, and shared libs reduce per-link memory pressure. No hard-coded limits — the build adapts to the machine. Document minimum build requirements.

### Claude's Discretion
- Specific mold integration approach in XMake (toolchain override vs linker flag)
- Optimal unity build batchsize values for dev vs CI
- Which internal libs need `__declspec(dllexport)` annotations vs can use def files
- ccache configuration details (cache size, hash strategy)
- Whether devbuild mode needs its own XMake config or can be a flag on existing modes
- Auto-detect implementation (XMake built-in vs custom script)

</decisions>

<specifics>
## Specific Ideas

- The 2.4GB vs 86MB gap (releasedbg vs release) proves split DWARF will have massive impact — debug info is 96% of archive size.
- Shared libs for dev only; release/releasedbg can keep static linking for single-DLL deployment simplicity.
- mold + split DWARF + shared libs is a three-pronged attack on the same bottleneck (link time). Each independently helps, together they should reduce 6+ minute builds to seconds for incremental changes.
- devbuild mode should be the default for `xmake -y` when developing — developers opt INTO optimization, not out of it.

</specifics>

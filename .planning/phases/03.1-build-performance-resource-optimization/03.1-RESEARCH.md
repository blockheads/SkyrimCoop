# Phase 03.1: Build Performance & Resource Optimization - Research

**Researched:** 2026-03-27
**Domain:** XMake build system optimization, MinGW cross-compilation linking, debug info management
**Confidence:** HIGH

## Summary

The phase targets three bottlenecks in the MinGW cross-compilation pipeline: link time (dominated by 2.4GB of static archives in releasedbg), compilation cache misses (full rebuilds on every change), and developer iteration speed (no fast-feedback build mode). The research confirms all seven decisions from CONTEXT.md are technically feasible with one critical correction: **mold does not support PE/COFF output** (Windows DLLs), so the linker acceleration must use **lld** (LLVM's linker) instead. lld-18 is already installed on the system, confirmed to work with MinGW GCC via `-fuse-ld=lld`, and is 2-5x faster than GNU ld on large inputs.

Split DWARF (`-gsplit-dwarf`) was verified to produce `.dwo` files with MinGW GCC 10 on this system. Combined with lld and shared internal libraries (using `--export-all-symbols` to avoid dllexport annotations), the three-pronged attack on link time should reduce 6+ minute full rebuilds to under 1 minute for incremental changes.

**Primary recommendation:** Replace mold with lld-18 as the fast linker, install ccache, create a `mode.devbuild` XMake rule with `-O0`/split-DWARF/lld/shared-libs, and keep `releasedbg` unchanged for runtime validation.

## Architecture Patterns

### Build Mode Architecture
```
xmake.lua (root)
  |-- add_rules("mode.debug", "mode.releasedbg", "mode.release")
  |-- rule("mode.devbuild")         # NEW: custom mode rule
  |       on_config: -O0, split-dwarf, symbols=debug
  |
  |-- if is_mode("devbuild") then
  |       set_policy("build.ccache", true)
  |       add_ldflags("-fuse-ld=lld")
  |       # Convert static targets to shared
  |
  |-- MinGW toolchain wrapper in .toolchain/bin/
  |       # Add ld.lld symlink here
```

### Pattern 1: Custom XMake Mode Rule
**What:** Define `mode.devbuild` as a custom rule following XMake's built-in mode pattern.
**When to use:** All devbuild-specific configuration.
**Example:**
```lua
-- Source: xmake mode rule pattern from xmake/rules/mode/xmake.lua
rule("mode.devbuild")
    on_config(function (target)
        if is_mode("devbuild") then
            -- No optimization for fastest compilation
            target:set("optimize", "none")
            -- Full debug symbols in split DWARF
            target:set("symbols", "debug")
        end
    end)
```

### Pattern 2: Conditional Static/Shared Library Kind
**What:** Use `is_mode("devbuild")` to switch `set_kind()` between static and shared.
**When to use:** All internal library targets in devbuild mode.
**Example:**
```lua
-- In each target definition
target("SkyrimEncoding")
    if is_mode("devbuild") then
        set_kind("shared")
        add_shflags("-Wl,--export-all-symbols", {force = true})
        set_prefixname("")  -- No "lib" prefix for Windows DLL names
    else
        set_kind("static")
    end
```

### Pattern 3: Linker Override via Toolchain Wrapper
**What:** Place `ld.lld` symlink in `.toolchain/bin/` so `-fuse-ld=lld` resolves correctly when using the wrapper GCC scripts.
**When to use:** Devbuild mode linker acceleration.
**Example:**
```lua
-- In xmake.lua mingw block, when devbuild mode
if is_plat("mingw") and is_mode("devbuild") then
    add_ldflags("-fuse-ld=lld", {force = true})
    add_shflags("-fuse-ld=lld", {force = true})
end
```

### Pattern 4: Split DWARF Integration
**What:** Add `-gsplit-dwarf` to compilation flags in devbuild mode.
**When to use:** Devbuild mode only -- reduces debug info in .o/.a files by 96%.
**Example:**
```lua
-- Inside mode.devbuild on_config or in mingw devbuild block
if is_plat("mingw") and is_mode("devbuild") then
    add_cxflags("-gsplit-dwarf", {force = true})
    -- Linker: use -Wl,--gdb-index to speed up debugger startup
    add_ldflags("-Wl,--gdb-index", {force = true})
end
```

### Anti-Patterns to Avoid
- **Global `-static` with shared libs:** The root xmake.lua adds `-static` to all MinGW builds. Devbuild shared libs need this removed for the shared targets (keep `-static-libgcc -static-libstdc++` for runtime, remove `-static` linker flag).
- **Unity build with shared libs:** Unity batches across TUs defeat the purpose of shared lib isolation. Devbuild should use smaller batchsize or disable unity entirely.
- **Modifying `releasedbg` mode:** Keep it unchanged for runtime validation. All optimizations go in `devbuild` only.
- **dllexport annotations:** `--export-all-symbols` makes this unnecessary for dev builds. Adding dllexport macros to every header is invasive and error-prone.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Fast linker | Custom link script | lld via `-fuse-ld=lld` | Drop-in replacement, handles PE/COFF natively |
| Build cache | Custom file hash cache | ccache via XMake `set_policy("build.ccache", true)` | XMake 2.6.6+ has built-in cross-platform build cache |
| Symbol export for shared libs | Per-header dllexport macros | `--export-all-symbols` linker flag | Zero code changes, works for all internal libs |
| Job count auto-detection | Custom RAM/CPU detection script | XMake built-in `-j` auto-detection | XMake already detects cores; just document minimum requirements |
| Custom mode definition | Separate config file | XMake `rule("mode.devbuild")` | Follows existing pattern, activates via `xmake f -m devbuild` |

**Key insight:** Every optimization in this phase is achievable through build system configuration changes only -- no C++ source code modifications are needed. This makes the phase low-risk and easily reversible.

## Common Pitfalls

### Pitfall 1: mold Cannot Produce PE/COFF
**What goes wrong:** mold is an ELF-only linker. Using it for MinGW cross-compilation targeting Windows DLLs fails immediately.
**Why it happens:** mold is frequently recommended as a fast linker, but its Windows support is still in early development (separate fork, not mainline).
**How to avoid:** Use lld (LLVM linker) instead. It has mature PE/COFF support and is already installed as lld-18.
**Warning signs:** Link errors mentioning unsupported output format.

### Pitfall 2: `-static` Flag Conflicts with Shared Libraries
**What goes wrong:** The root xmake.lua adds `-static` globally for MinGW. This flag tells the linker to prefer static versions of ALL libraries, which conflicts with building shared internal libs.
**Why it happens:** `-static` was needed for release builds to avoid runtime DLL dependencies.
**How to avoid:** In devbuild mode, remove the blanket `-static` from ldflags but keep `-static-libgcc -static-libstdc++` (these specifically target the GCC runtime, not user libraries).
**Warning signs:** Linker warnings about static/shared mixing; shared libs not actually being built as DLLs.

### Pitfall 3: Import Library Stale Artifacts
**What goes wrong:** The existing `before_link` hook in `Code/client/xmake.lua` cleans stale `.dll.a` import libs. With multiple shared internal libs, stale import libs from previous builds can cause wrong library resolution.
**Why it happens:** MinGW generates import libraries (`.dll.a`) alongside DLLs. If a build fails mid-way, stale import libs remain.
**How to avoid:** Extend the `before_link` cleanup pattern to all shared lib targets in devbuild mode, or add a clean step.
**Warning signs:** Linking succeeds but the wrong version of a library is used at runtime.

### Pitfall 4: ccache and Force-Include Flags
**What goes wrong:** The project uses `-include TiltedOnlinePCH.h` and `-include MinGWCompat.h` as force-include flags. ccache may not hash these files correctly if they're specified via `add_cxflags` rather than proper PCH configuration.
**Why it happens:** ccache hashes the command line and input files. Force-included files need to be part of the hash.
**How to avoid:** XMake's built-in build cache (post-2.6.6) handles this. Alternatively, set `CCACHE_EXTRAFILES` to include the force-included headers.
**Warning signs:** Code changes in PCH or MinGWCompat.h don't trigger recompilation.

### Pitfall 5: Split DWARF and GDB on Wine
**What goes wrong:** `.dwo` files are separate from the DLL. If the DLL is deployed to a Proton/Wine prefix, GDB needs access to the `.dwo` files in the original build directory.
**Why it happens:** Split DWARF stores a path reference in the binary pointing to where `.dwo` files were at compile time.
**How to avoid:** For debugging, always run GDB from the build directory, or set `set debug-file-directory` in GDB to point to the build output.
**Warning signs:** GDB says "Could not find DWO" and shows no source-level debug info.

### Pitfall 6: Unity Build Batchsize vs Incremental Build Speed
**What goes wrong:** With batchsize=12, changing one `.cpp` file recompiles 12 files. This negates the benefit of ccache for touched files and slows iteration.
**Why it happens:** Unity build is designed for clean build speed, not incremental speed.
**How to avoid:** Use batchsize=1 or disable unity build entirely in devbuild mode. Keep batchsize=12 for release/CI builds.
**Warning signs:** Incremental build recompiles many more files than expected.

## Open Questions

1. **lld symlink placement**
   - What we know: `-fuse-ld=lld` requires `ld.lld` to be in PATH. The system has `ld.lld-18` but GCC looks for `ld.lld`.
   - What's unclear: Whether to put the symlink in `.toolchain/bin/` (project-local) or `/usr/local/bin/` (system-wide).
   - Recommendation: Add to `.toolchain/bin/` for project self-containment; document the system-wide alternative.

2. **Shared lib dependency ordering**
   - What we know: Internal libraries have complex dependency chains (e.g., SkyrimTogetherServer depends on SkyrimCoopNetworking, CommonLib, BaseLib, etc.).
   - What's unclear: Whether XMake handles shared lib link ordering automatically in devbuild, or if we need explicit DLL search paths.
   - Recommendation: Start with the final DLL target only using shared internal libs; iterate based on link errors.

3. **devbuild as default mode**
   - What we know: CONTEXT.md says "devbuild should be the default for `xmake -y` when developing."
   - What's unclear: XMake's `xmake -y` uses the configured mode (`xmake f -m devbuild`). There's no way to make a mode the "default" without changing the config.
   - Recommendation: Document `xmake f -p mingw -m devbuild` as the developer setup command. Do not change the default mode (it would break CI).

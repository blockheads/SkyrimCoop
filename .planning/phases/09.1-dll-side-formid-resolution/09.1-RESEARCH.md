# Phase 09.1: DLL-Side FormId Resolution - Research

**Researched:** 2026-03-28
**Domain:** Wine address space isolation, MinGW DLL memory access, TCP relay protocol modification
**Confidence:** HIGH

## Summary

Phase 09.1 closes Gap 1 from Phase 09 verification: Wine heap addresses (0x20x-0x86x range) are not accessible from Linux via `/proc/pid/mem` because Wine's guest virtual address space differs from the host Linux process address space. The relay DLL currently sends raw `void*` pointers in HookEventPacket args, and the native Linux process passes these directly to `pread()` which operates on host file offsets -- 100% failure rate confirmed by human testing.

The fix is architecturally simple but mechanically extensive: the DLL (running inside Wine/Skyrim) must read formIds, positions, and other game data **inside the Wine process** where the pointers are valid, then pack the resolved VALUES into the HookEventPacket before sending over TCP. The native side stops doing `pread()`-based memory reads for hook event data and instead consumes the values directly from the packet.

This affects every hook trampoline in `hook_trampolines.cpp` (~31 hooks), the protocol definition in `protocol.h`, every service's `OnHookEvent()` handler in the native client (8 services), and the main event loop dispatcher in `main.cpp`. The changes are mechanical and repetitive but must be precise about which pointer args get dereferenced in the DLL vs. which scalar values pass through unchanged.

**Primary recommendation:** Define per-opcode "enriched" packet structures where pointer args are replaced by the formId/position/float values that the native side needs. The DLL reads `*(uint32_t*)(ptr + 0x14)` to get formId and `*(float*)(ptr + 0x54)` for position directly in the trampoline. The native side consumes these values without any `pread()` calls for hook-event-driven data.

## Architecture Patterns

### Current Architecture (Broken)

```
DLL trampoline:
  HookActorAdded(void* apThis) {
    args[0] = reinterpret_cast<uint64_t>(apThis);  // Wine guest pointer
    SendHookEvent(HOOK_ACTOR_ADDED, 1, args);       // sends raw pointer
  }

Native client receives:
  uint64_t actorPtr = hookPkt.args[0];  // Wine guest address: 0x200000XXXX
  uint32_t formId = pread(fd, buf, 4, actorPtr + 0x14);  // FAILS: not a host vaddr
```

### Fixed Architecture

```
DLL trampoline:
  HookActorAdded(void* apThis) {
    // Read game data INSIDE Wine where pointer is valid
    uint32_t formId = *(uint32_t*)((uintptr_t)apThis + 0x14);
    float posX = *(float*)((uintptr_t)apThis + 0x54);
    float posY = *(float*)((uintptr_t)apThis + 0x58);
    float posZ = *(float*)((uintptr_t)apThis + 0x5C);
    // Pack resolved values into packet
    ActorAddedPacket pkt{};
    pkt.formId = formId;
    pkt.posX = posX; pkt.posY = posY; pkt.posZ = posZ;
    pkt.rawPtr = (uint64_t)apThis;  // keep for CMD_SET_POSITION targeting
    SendRichHookEvent(HOOK_ACTOR_ADDED, &pkt, sizeof(pkt));
  }

Native client receives:
  uint32_t formId = actorAddedPkt.formId;  // direct value, no pread needed
```

### Design Decision: Enriched Packets vs. Generic Args

**Two approaches considered:**

1. **Enriched per-opcode packets:** Each hook opcode has its own struct with named fields. DLL packs values, native unpacks by struct type. Type-safe, self-documenting, but changes the protocol format significantly.

2. **Resolve-in-place in generic args:** Keep HookEventPacket unchanged but put formIds where pointers used to go (`args[0] = formId` instead of `args[0] = ptr`). Minimal protocol change but loses the raw pointer information needed for CMD_SET_POSITION targeting of remote actors.

**Recommendation: Hybrid approach.**

Keep `HookEventPacket` as the wire format (backward-compatible, no protocol struct changes needed). Use a convention: **every pointer arg is followed by its resolved formId in the next arg slot**. For essential hooks that also need position data, pack float values using the existing `FloatToU64()` helper.

Specifically for the critical hooks:

| Hook | Current args | New args |
|------|-------------|----------|
| HOOK_CHARACTER_CTOR / HOOK_SPAWN_ACTOR / HOOK_ACTOR_PROCESS | `[ptr]` | `[ptr, formId]` |
| HOOK_SET_POSITION | `[refPtr, posPtr]` | `[refPtr, formId, posX_u64, posY_u64, posZ_u64]` |
| HOOK_DEATH_ITEMS | `[actorPtr]` | `[actorPtr, formId]` |
| HOOK_ADD_INVENTORY | `[actorPtr, itemPtr, count, ...]` | `[actorFormId, itemFormId, count, actorPtr]` |
| HOOK_SPELL_CAST | `[casterPtr, spellPtr]` | `[casterFormId, spellFormId, casterPtr]` |
| HOOK_SET_WEATHER / HOOK_FORCE_WEATHER | `[skyPtr, weatherPtr, flag]` | `[skyPtr, weatherFormId, flag]` |
| HOOK_DAMAGE_ACTOR | `[actorPtr, damage]` | `[actorFormId, damage, actorPtr]` |

This keeps the `HookEventPacket` struct unchanged (still 8 args max) while delivering resolved values. The raw pointer is still available (in a different arg slot) for services that need it for CMD targeting.

### What the DLL Must Read (Memory Offsets)

These offsets are already known and used in the native client's `game_reader.cpp` and `CharacterService.h`:

| Offset | Type | Field | Used By |
|--------|------|-------|---------|
| +0x14 | uint32_t | TESForm::formID | Every service that identifies actors/items |
| +0x54 | float[3] | TESObjectREFR::position (NiPoint3) | CharacterService position sync |
| +0x60 | float | TESObjectREFR::rotation.x | CharacterService rotation sync |
| +0x68 | float | TESObjectREFR::rotation.z | CharacterService rotation sync |

The DLL already runs inside the Skyrim process, so `*(uint32_t*)((uintptr_t)ptr + 0x14)` is a direct memory read -- no system call, no Wine translation needed. These are standard Skyrim SE struct layouts stable across the 1.6.x runtime.

### Anti-Patterns to Avoid

- **Reading complex struct chains in DLL:** The DLL should only read flat offsets (+0x14 for formId, +0x54 for position). Do NOT follow pointer chains (e.g., ActorValueOwner vtable) in the DLL -- that is too fragile and complex. CalendarService's `ReadChain()` calls remain as periodic native-side polling.
- **Removing ProcMemReader entirely:** Some services (CalendarService, CharacterService::SyncMovement) still need periodic memory polling for data that arrives via position reads, not hooks. Keep pread for now.
- **Introducing new DLL dependencies:** Per Phase 7 D-13, the DLL must remain MinHook + winsock2 only. No spdlog, no EnTT, no game struct headers.
- **Breaking the generic HookEventPacket format:** Changing the packet struct would break --record replay compatibility and the mock_skyrim_loader test tool. Keep the struct, change the arg semantics.
- **Null pointer dereference in DLL trampolines:** Hook arguments CAN be null (e.g., `apItem = nullptr` in inventory hooks). Always guard: `uint32_t formId = (apThis != nullptr) ? *(uint32_t*)((uintptr_t)apThis + 0x14) : 0;`

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Wine address translation | Guest-to-host addr mapping | Read values in DLL | Translation is impossible without Wine internals |
| New protocol format | Custom per-opcode structs | Reuse HookEventPacket with new arg conventions | Avoids protocol version mismatch, keeps --record compatible |
| DLL-side logging framework | spdlog port to DLL | OutputDebugStringA + RelayLog() | Per D-13, DLL stays minimal |
| Position packing | Custom float-to-int encoding | Existing FloatToU64() helper | Already used, proven working |

**Key insight:** Wine address translation from the native side is fundamentally impossible -- Wine's virtual memory manager does not expose a guest-to-host mapping. Reading inside the DLL is the only viable approach. This is not a workaround; it is the correct architecture.

## Common Pitfalls

### Pitfall 1: Null Pointer Dereference in DLL Trampolines
**What goes wrong:** Skyrim crashes because a hook trampoline tries to read formId from a null pointer.
**Why it happens:** Game engine sometimes passes nullptr for optional parameters (e.g., apExtraData in inventory hooks).
**How to avoid:** Guard every dereference: `uint32_t formId = (ptr != nullptr) ? *(uint32_t*)((uintptr_t)ptr + 0x14) : 0;`. Send formId=0 for null pointers and let the native side handle gracefully (it already does: `if (formId == 0) return;`).
**Warning signs:** Skyrim crashes in a hook trampoline with access violation at address 0x14.

### Pitfall 2: DLL Reads Partially Constructed Objects
**What goes wrong:** formId reads as 0 for objects still being constructed.
**Why it happens:** CharacterCtor hooks fire during construction. The formId field at +0x14 may not be populated yet.
**How to avoid:** For constructor hooks (HOOK_CHARACTER_CTOR), send formId=0 and the raw pointer. The native side already has `ReadFormIdDeferred()` with retry logic. Alternatively, defer formId read to SpawnActorInWorld which fires after construction completes.
**Warning signs:** ActorAdded events with formId=0 for valid actors.

### Pitfall 3: Changing Arg Layout Without Updating All Consumers
**What goes wrong:** Native services crash or read garbage because they expect the old arg layout.
**Why it happens:** 8 services + main.cpp dispatcher all consume HookEventPacket args. Miss one, get corruption.
**How to avoid:** Define the arg layout in protocol.h comments. Update all consumers systematically -- the grep output shows exactly which files and lines call ReadFormId on hook args.
**Warning signs:** Wrong formIds (e.g., position float bits interpreted as formId).

### Pitfall 4: Losing Raw Pointers Needed for CMD Commands
**What goes wrong:** CMD_SET_POSITION cannot target remote actors because the native side no longer knows the Wine pointer.
**Why it happens:** If we completely replace pointer args with formIds, we lose the CMD targeting info.
**How to avoid:** Always include the raw pointer in the packet alongside the resolved formId. For actor lifecycle hooks: `args[0] = rawPtr, args[1] = formId`. Native side uses formId for identification, stores rawPtr for CMD targeting.
**Warning signs:** Remote actor positions not updating (CMD_SET_POSITION targets wrong/zero address).

### Pitfall 5: Breaking mock_skyrim_loader Test Pipeline
**What goes wrong:** CI mock relay pipeline fails because mock_skyrim_loader sends old-format packets.
**Why it happens:** mock_skyrim_loader.cpp also creates HookEventPackets manually for testing.
**How to avoid:** Update mock_skyrim_loader.cpp to pack formId values in the new arg positions. Simple change -- it's ~150 LOC.
**Warning signs:** CI pipeline (ci_test.sh step 4) fails after protocol changes.

### Pitfall 6: Position Polling Still Uses pread (SyncMovement)
**What goes wrong:** CharacterService::SyncMovement() still reads positions via pread, which still fails.
**Why it happens:** SyncMovement is a periodic poll, not hook-driven. It reads actor positions from the pointer table using stored Wine pointers.
**How to avoid:** Two options: (A) Add a periodic position report mechanism in the DLL (e.g., DLL sends position updates for tracked actors every 100ms), or (B) Use HOOK_SET_POSITION events to cache latest position in native side and use cached values instead of pread. Option B is simpler and sufficient for Phase 9.1 MVP.
**Warning signs:** "Failed to read actor position at 0x20..." in native logs during movement sync.

## Code Examples

### DLL Trampoline: Reading FormId Inside Wine

```cpp
// Source: proposed modification to hook_trampolines.cpp
// Helper: safely read formId (TESForm::formID at +0x14)
static uint32_t ReadFormId(void* apForm)
{
    if (!apForm) return 0;
    return *reinterpret_cast<uint32_t*>(
        reinterpret_cast<uintptr_t>(apForm) + 0x14);
}

// Helper: safely read NiPoint3 position (at +0x54)
static void ReadPosition(void* apRef, float* aOutX, float* aOutY, float* aOutZ)
{
    if (!apRef) { *aOutX = *aOutY = *aOutZ = 0.0f; return; }
    uintptr_t base = reinterpret_cast<uintptr_t>(apRef);
    *aOutX = *reinterpret_cast<float*>(base + 0x54);
    *aOutY = *reinterpret_cast<float*>(base + 0x58);
    *aOutZ = *reinterpret_cast<float*>(base + 0x5C);
}
```

### Modified HookSpawnActor Trampoline

```cpp
// Source: proposed modification to hook_trampolines.cpp
static void __fastcall HookSpawnActor(void* apThis)
{
    uint32_t formId = ReadFormId(apThis);
    float posX, posY, posZ;
    ReadPosition(apThis, &posX, &posY, &posZ);

    uint64_t args[6] = {
        reinterpret_cast<uint64_t>(apThis),  // [0] raw ptr (for CMD targeting)
        static_cast<uint64_t>(formId),        // [1] resolved formId
        FloatToU64(posX),                     // [2] position X
        FloatToU64(posY),                     // [3] position Y
        FloatToU64(posZ),                     // [4] position Z
        0                                     // [5] reserved
    };
    SendHookEvent(HOOK_SPAWN_ACTOR, 6, args);
    RealSpawnActor(apThis);
}
```

## Scope Analysis: What Remains on pread

After this phase, `pread()` is still used for:

| Caller | What It Reads | Why Not DLL-Side |
|--------|--------------|------------------|
| CharacterService::SyncMovement() | Actor positions every 100ms | Periodic poll, not hook-driven. **Phase 9.1 can eliminate this by caching positions from HOOK_SET_POSITION events.** |
| CharacterService::SyncMovement() | Actor rotations | Same as above. |
| CalendarService::Update() | GameHour/Day/Month/Year via pointer chain | Complex chain dereference, only works if Calendar singleton ptr is valid. **Still broken until a DLL-side calendar hook is added. Low priority.** |
| WeatherService::PollCurrentWeather() | Sky singleton -> current weather | Pointer chain. **Still broken. Low priority.** |
| MagicService handlers | Spell casting type, effect magnitude/duration | Deep struct reads from apArgs[1] sub-fields. **Can be moved to DLL but complex. Medium priority.** |
| HandlePerformAction | ActionEvent fields at offsets 0, 4 | Reads from aActionEventPtr. **Can be moved to DLL.** |

**Phase 9.1 MVP scope:** Resolve formIds and positions for ALL hook events. Cache HOOK_SET_POSITION position data so SyncMovement can use cached values instead of pread. This unblocks CharacterService (the critical path for actor sync). CalendarService and deep MagicService reads remain stubbed/broken -- they were already non-functional and are not required for basic actor sync.

## Open Questions

1. **Constructor hook timing for formId**
   - What we know: CharacterCtor fires during object construction. formId at +0x14 might not be populated yet.
   - What's unclear: Whether SpawnActorInWorld always fires after formId is set.
   - Recommendation: Read formId in all constructor hooks. If 0, send 0 and let native side ignore. SpawnActorInWorld is the reliable insertion point. Test will confirm.

2. **Position cache staleness for SyncMovement**
   - What we know: HOOK_SET_POSITION fires when the game engine sets actor positions. SyncMovement polls at 100ms.
   - What's unclear: How frequently HOOK_SET_POSITION fires for the player character. If it fires per-frame, the cache will be very fresh. If it fires only on teleports, it may miss interpolated movement.
   - Recommendation: Implement position cache from HOOK_SET_POSITION. If it proves too coarse, a future phase can add a periodic DLL-side position reporter.

3. **mock_skyrim_loader update scope**
   - What we know: mock_skyrim_loader.cpp sends scripted HookEventPackets with fake data.
   - What's unclear: Whether it needs to send realistic formIds for the CI pipeline to pass.
   - Recommendation: Update to new arg layout. Use well-known formIds (0x14 for player, 0x10 for Whiterun) in mock data.

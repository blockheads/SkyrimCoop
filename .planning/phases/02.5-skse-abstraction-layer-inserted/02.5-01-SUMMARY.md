# Phase 02.5 Plan 01: Bridge Interface Definitions and Skeleton Implementations Summary

Five pure-virtual bridge interface headers defined with 120+ total methods covering all SKSE call sites across 14 service files; SkyrimBridge and ReplayBridge skeletons created with compilation boundary enforced via new xmake targets.

## What Was Built

### Task 1: Five Bridge Interface Headers

**IActorBridge.h** (41 pure virtuals) — All Actor* operations: existence, remote/player flags, movement, actor values, equipment, animation graph hashes, magic casters, spell casting, inventory state, combat targets, base form access.

**IFormBridge.h** (28 pure virtuals) — TESForm lookups, TESGlobal get/set, cell/worldspace lookups, quest queries and mutations, mod registry access, typed spell/magic item checks.

**IPlayerBridge.h** (33 pure virtuals) — PlayerCharacter::Get() and all pPlayer->* operations: position, cell/worldspace, waypoints, movement, death/bleeding, god mode, respawn, difficulty, level, spells, race, quests, HUD messaging.

**IEventBridge.h** (8 pure virtuals) — EventDispatcherManager::Get() sink registrations wrapped as typed callbacks (std::function), plus inject methods for ReplayBridge to synthesise events in tests.

**IWorldBridge.h** (10 pure virtuals) — Sky::Get() weather operations and mod list access, game weather system toggle, game time get/set.

**Design constraints enforced:**
- No SKSE type (`Actor*`, `TESForm*`, `Sky*`, etc.) in any interface signature
- All parameters and returns are primitives: `uint32_t`, `float`, `bool`, `std::string`, `std::vector<T>`
- All methods are `noexcept` per project coding guidelines

### Task 2: Implementation Skeletons + Build Targets

**SkyrimBridge** (h + cpp) — Real SKSE implementation; only file in the bridge layer allowed to include SKSE headers. Implements:
- NDJSON recording infrastructure: `StartRecording`, `StopRecording`, `RecordCall`, `RecordReturn` with mutex-protected std::ofstream
- ~40 fully-implemented methods (actor lookup, player form, weather, equip spells, etc.)
- ~80 TODO stubs with `spdlog::warn` for methods that need actor manipulation details filled in Plans 02/03

**ReplayBridge** (h + cpp) — Zero SKSE dependency. Implements:
- `LoadRecording()`: reads NDJSON lines into `m_eventLines`
- All methods return safe defaults (false/0/empty)
- Event callbacks stored and dispatched via `InjectQuestStartStopEvent` etc.
- Compiles without `Games/Skyrim` on the include path

**Code/client/xmake.lua changes:**
- `SkyrimBridge.cpp` added to `SkyrimTogetherClient` (SKSE-bearing target)
- New `SkyrimTogetherClientServices` static lib target: compiles Services + ReplayBridge, include path deliberately excludes `Games/Skyrim` — this is the compilation boundary enforcer

**Code/tests/client_replay/:**
- `xmake.lua`: `ClientReplayTests` binary target (no SKSE deps)
- `client_replay_tests.cpp`: Two Catch2 test cases — bridge instantiation smoke test + event injection test

## Known Stubs

SkyrimBridge.cpp contains ~80 TODO stub methods that log a warning and return defaults. These are intentional and expected at this stage — Plans 02.5-02 and 02.5-03 will replace each stub with real SKSE calls as individual services are migrated. The stubs are tagged with `// TODO(02.5-02)` for tracking.

Key stubs:
- `SkyrimBridge::SetActorValue` — needs ActorValueOwner::SetActorValue
- `SkyrimBridge::EquipItem/UnequipItem` — needs EquipManager full call
- `SkyrimBridge::DrawWeapon` — needs actor state manipulation
- `SkyrimBridge::ForceWeather` — needs Sky::ForceWeather implementation
- `SkyrimBridge::RegisterQuestStartStopSink` — needs EventDispatcherManager plumbing

None of these stubs affect this plan's goal (defining the contracts and proving the boundary architecture).

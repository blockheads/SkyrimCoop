# Phase 2.5: SKSE Abstraction Layer - Research

**Researched:** 2026-03-30
**Domain:** C++ interface abstraction, SKSE game API isolation, NDJSON recording/replay
**Confidence:** HIGH (all findings from direct source code inspection)

## Summary

Phase 2.5 abstracts all Skyrim/SKSE API calls behind focused bridge interfaces so that client services in `Code/client/Services/` can compile and run headlessly without a live Skyrim process. The real `SkyrimBridge` calls SKSE and game memory; a `ReplayBridge` returns pre-recorded canned responses during testing.

The central design challenge is **pointer opacity**: services don't just call lookup functions — they receive raw `Actor*`, `TESForm*`, `Sky*` pointers and immediately call methods on them (e.g., `pActor->GetExtension()->SetRemote(true)`, `pActor->Kill()`, `Sky::Get()->ForceWeather(...)`). A bridge must either wrap those pointer operations too (fat bridge, many interface methods) or refactor services to never hold raw pointers (thin handle-based bridge, more service changes). The approach chosen determines the scope of every service migration task.

The phase additionally needs a new xmake build target — a headless test binary that links `Code/client/Services/` against `ReplayBridge` instead of real SKSE headers. The existing `ReplayTests` xmake.lua currently references the old `native_client/` architecture and is not reusable without changes.

**Primary recommendation:** Use the fat-bridge (wrap-every-dereference) approach because it minimizes service code changes — services already work correctly with game objects; the bridge just needs to provide mock objects that respond to the same method calls via virtual dispatch or stub structs. Migrate services in ascending order of SKSE call count (simplest first) to reduce risk.

### Pattern 1: Fat Bridge (Recommended)

**What:** Each bridge interface provides methods for every distinct game operation currently called through a pointer. Services call `m_bridge.SetActorRemote(formId, true)` instead of `pActor->GetExtension()->SetRemote(true)`.

**When to use:** When services currently hold raw game object pointers and chain multiple operations on them. Minimizes service logic changes — service behavior is preserved.

**Example:**
```cpp
// Code/client/Bridges/IActorBridge.h
// Source: direct analysis of CharacterService.cpp call sites
class IActorBridge
{
public:
    virtual ~IActorBridge() = default;

    // Form lookup
    [[nodiscard]] virtual Actor* GetActorById(uint32_t aFormId) const noexcept = 0;

    // State mutations (recorded as NDJSON events in SkyrimBridge)
    virtual void SetActorRemote(uint32_t aFormId, bool aRemote) noexcept = 0;
    virtual void SetActorPlayer(uint32_t aFormId, bool aPlayer) noexcept = 0;
    virtual void DeleteActor(uint32_t aFormId) noexcept = 0;
    virtual void KillActor(uint32_t aFormId) noexcept = 0;
    virtual void RespawnActor(uint32_t aFormId) noexcept = 0;
    virtual void MoveActorTo(uint32_t aFormId, TESObjectCELL* apCell, const NiPoint3& aPos) noexcept = 0;

    // State queries (return value recorded as NDJSON "return" field in SkyrimBridge)
    [[nodiscard]] virtual bool IsActorDead(uint32_t aFormId) const noexcept = 0;
    [[nodiscard]] virtual bool IsActorMount(uint32_t aFormId) const noexcept = 0;
    [[nodiscard]] virtual bool IsActorPlayerSummon(uint32_t aFormId) const noexcept = 0;
    [[nodiscard]] virtual float GetActorValue(uint32_t aFormId, int aIndex) const noexcept = 0;

    // ... additional methods from call-site inventory
};
```

**Why fat bridge over thin/handle-based bridge:**
- Services contain 100+ pointer dereferences in CharacterService alone. A handle-based approach requires refactoring every chain.
- Service correctness depends on the game objects' method semantics. With fat bridge, the service logic is preserved verbatim.
- Interface methods map 1:1 to recording events, making the NDJSON schema mechanical.

### Pattern 2: Bridge Injection via World::ctx()

**What:** Bridge instances are stored in World's entt::registry context, accessed by services the same way they already access other dependencies.

**When to use:** Always — consistent with existing codebase injection pattern (D-01 from World.h, services already use `m_world.ctx().at<PartyService>()`).

**Example:**
```cpp
// World constructor (Code/client/World.cpp)
// Real game: creates SkyrimBridge, injects into ctx
ctx().emplace<IActorBridge&>(/* SkyrimBridge instance */);
ctx().emplace<IFormBridge&>(/* SkyrimBridge instance */);

// Service constructor: retrieves bridge from world context
CharacterService::CharacterService(World& aWorld, ...)
    : m_actorBridge(aWorld.ctx().at<IActorBridge>())
    , m_formBridge(aWorld.ctx().at<IFormBridge>())
    ...
```

**Headless test binary: creates ReplayBridge, injects same way**
```cpp
// ClientReplayHarness constructor
ctx().emplace<IActorBridge&>(m_replayBridge);
ctx().emplace<IFormBridge&>(m_replayBridge);
```

### Pattern 3: NDJSON Schema (client-side, distinct from server-side enet schema)

**What:** Every bridge call is recorded as a single-line JSON object with: op (method name), direction (call vs. return), form IDs, and typed payload.

**Example schema lines:**
```json
{"op":"GetActorById","formId":"0x14","dir":"call","ts":0.001}
{"op":"GetActorById","formId":"0x14","dir":"return","result":true,"ts":0.001}
{"op":"SetActorRemote","formId":"0x14","remote":true,"dir":"call","ts":0.002}
{"op":"IsActorDead","formId":"0x14","dir":"call","ts":0.003}
{"op":"IsActorDead","formId":"0x14","dir":"return","result":false,"ts":0.003}
{"op":"DeleteActor","formId":"0xFF12AB","dir":"call","ts":0.004}
```

**Key design distinctions from server-side enet schema:**
- No `payload` base64 field — these are game API calls, not binary messages
- No `peer` field — single-client recording
- `op` is method name string, not opcode integer
- Queries have both `call` and `return` entries; mutations have only `call` (no meaningful return to record)
- `ts` is seconds since session start (same pattern as EnetRecorder)

### Anti-Patterns to Avoid

- **Including SKSE headers in bridge interface headers.** Interface headers must be includable without SKSE. Only `SkyrimBridge.cpp` includes SKSE headers. If `Actor*` appears in an interface signature, it must forward-declare or use `uint32_t` form IDs instead.
- **One monolithic bridge.** CharacterService needs 20+ actor methods. ActorValueService needs 8+. A single class becomes unnavigable. Split by logical concern per D-01.
- **Partial rollout.** D-02 is clear: all 24 services migrate in this phase. A partial rollout leaves the compilation boundary unchecked — the verification test (compile services without SKSE headers) fails if even one service retains a direct game call.
- **Referencing native_client in new test target.** The existing `Code/tests/replay/xmake.lua` adds files from `../../native_client/`. The new `ClientReplayTests` target must reference `Code/client/` services and `Code/client/Bridges/ReplayBridge` only. Do not extend the existing xmake.lua target.

## Common Pitfalls

### Pitfall 1: Pointer Opacity — Bridge Methods That Return Raw Pointers

**What goes wrong:** Bridge interface declares `Actor* GetActorById(uint32_t)`. Services receive the pointer and call methods on it. ReplayBridge has no real `Actor` objects — it can't return a valid pointer.

**Why it happens:** Direct translation of `Cast<Actor>(TESForm::GetById(...))` to a bridge method preserves the pointer return type.

**How to avoid:** Two options:
- Option A (recommended): Bridge methods perform the full operation, not just the lookup. `bridge.SetActorRemote(formId, true)` rather than `auto* p = bridge.GetActorById(formId); p->GetExtension()->SetRemote(true)`. Services never hold `Actor*` at the call site.
- Option B: Return a virtual `IActor` handle that wraps all `Actor*` methods. More complex but allows services to keep chains like `bridge.GetActor(formId)->SetRemote(true)`.

Decision is Claude's discretion per CONTEXT.md, but Option A is simpler and sufficient for the headless test goal.

**Warning signs:** Bridge interface has a method that returns `Actor*`, `TESForm*`, or any other raw game type pointer.

### Pitfall 2: Event Sink Registration in Constructors

**What goes wrong:** QuestService constructor calls `EventDispatcherManager::Get()->questStartStopEvent.RegisterSink(this)`. ObjectService calls `EventDispatcherManager::Get()->activateEvent.RegisterSink(this)`. In headless mode, `EventDispatcherManager::Get()` dereferences Skyrim memory — it crashes.

**Why it happens:** These are not form lookups or actor operations — they're game engine event subscriptions. The adapter pattern used for `TESForm::GetById` doesn't cover them.

**How to avoid:** `IEventBridge` must provide `RegisterQuestSink(...)` and `RegisterActivateSink(...)` methods. `SkyrimBridge` calls `EventDispatcherManager::Get()`. `ReplayBridge` synthesizes events via the NDJSON replay file. This is the key motivation for D-01's separate `IEventBridge` grouping.

**Warning signs:** Service constructor calls `EventDispatcherManager::Get()` directly without going through a bridge.

### Pitfall 3: Header Contamination — SKSE Types Leaking Into Interface Headers

**What goes wrong:** `IActorBridge.h` forward-declares `class Actor` or `struct TESNPC`. Any service that includes `IActorBridge.h` may transitively pull in SKSE definitions through a PCH or other include.

**Why it happens:** Convenient to reuse existing types; hard to see transitive includes.

**How to avoid:** Interface headers use only primitive types: `uint32_t` for form IDs, `float` for positions/values, `bool` for state flags. All SKSE types stay in `SkyrimBridge.cpp`. Verify by compiling bridge interface headers without the SKSE PCH.

**Warning signs:** `#include <Actor.h>`, `#include <PlayerCharacter.h>`, or any other Skyrim type appears in a Bridges/*.h interface file.

### Pitfall 4: OverlayService Scope Confusion

**What goes wrong:** Plan assumes OverlayService needs bridge migration because it has 11 SKSE calls. In practice, the entire `OverlayService.cpp` is wrapped in `#ifdef HAS_CEF`. MinGW builds (the target platform per BUILD-01) compile OverlayService out entirely — first line is `#ifdef HAS_CEF`, last line is `#endif`.

**Why it happens:** Context.md lists OverlayService as having 11 SKSE calls without noting the CEF guard.

**How to avoid:** Confirm which services are guarded by `#ifdef HAS_CEF` or `#ifdef HAS_DISCORD`. Calls inside those guards are only reachable on non-MinGW builds. MinGW bridge migration can skip those call sites, but the plan should document the decision explicitly so it doesn't look like an oversight.

**Warning signs:** Plan includes OverlayService as a migration task without noting the `#ifdef HAS_CEF` guard.

### Pitfall 5: Mutations vs Queries in NDJSON Recording

**What goes wrong:** Recording code records `pActor->Kill()` (a mutation) the same way as `pActor->IsDead()` (a query). ReplayBridge treating mutations as queries (expecting a return value) causes schema mismatch.

**Why it happens:** Both are bridge method calls; the recording loop doesn't distinguish them.

**How to avoid:** NDJSON schema must distinguish mutation events (no `return` entry needed — the effect was recorded) from query events (both `call` and `return` entries needed so ReplayBridge knows what to return). Mutations log `{"op":"DeleteActor","formId":"0xFF12AB","dir":"call"}`. Queries log a `call` entry and a `return` entry with the actual value recorded.

**Warning signs:** ReplayBridge replay code looks up return values for void-returning bridge methods.

### Pitfall 6: new xmake.lua Target References native_client

**What goes wrong:** Developer adds client replay tests by extending the existing `ReplayTests` xmake target, which already references `../../native_client/`. This creates a dependency on the old architecture.

**Why it happens:** The `ReplayTests` target in `Code/tests/replay/xmake.lua` is the nearest reference and appears to already do "client replay." But it uses `native_client/` services, not `Code/client/Services/`.

**How to avoid:** Create a new, separate `ClientReplayTests` target in a new `Code/tests/client_replay/xmake.lua` (or a new target in the existing xmake.lua). It links against `SkyrimTogetherClient` (the static client lib) and the new `ReplayBridge`. It explicitly excludes `native_client/` includes.

## Interface Grouping (Recommended)

Based on actual call-site analysis across all services:

### IActorBridge
Covers: `Cast<Actor>(TESForm::GetById(...))` lookups and all `pActor->*` method calls.
Key methods: `ActorExists`, `SetActorRemote`, `IsRemotePlayer`, `IsActorDead`, `KillActor`, `RespawnActor`, `DeleteActor`, `MoveActorTo`, `GetActorValue`, `GetActorFactions`, `SetActorFactions`, `GetActorInventory`, `SetActorInventory`, `SetActorValues`, `IsPlayerSummon`, `IsTemporaryActor`, `GetCommandingActor`

### IFormBridge
Covers: `TESForm::GetById`, `Cast<TESObjectCELL>`, `Cast<TESWorldSpace>`, `Cast<TESWeather>`, `Cast<TESNPC>`, `Cast<TESGlobal>` — general form resolution by ID.
Key methods: `GetFormById<T>()` template or typed overloads per TESForm subtype, `GetCellById`, `GetWorldSpaceById`, `GetWeatherById`

### IPlayerBridge
Covers: `PlayerCharacter::Get()` and all `pPlayer->*` method calls.
Key methods: `GetPlayerFormId`, `GetPlayerPosition`, `GetPlayerCell`, `GetPlayerBaseNpc`, `GetPlayerInventory`, `GetPlayerObjectives`, `GetPlayerMods`, `IsScriptExtenderLoaded`

### IEventBridge
Covers: `EventDispatcherManager::Get()->*.RegisterSink(...)` and `EventDispatcherManager::Get()->*.UnregisterSink(...)`.
Key methods: `RegisterQuestStartStopSink`, `RegisterQuestStageSink`, `RegisterActivateSink`, `UnregisterAll`
Note: ReplayBridge synthesizes these events from NDJSON rather than Skyrim's live event pump.

### IWorldBridge
Covers: `Sky::Get()`, `ModManager::Get()`, `ModManager::mods` iteration.
Key methods: `GetCurrentWeatherId`, `ForceWeather`, `GetModList`, `GetModCount`

## Open Questions

1. **Return type pollution: can `Actor*` appear in IActorBridge?**
   - What we know: If bridge interface returns `Actor*`, interface headers must include or forward-declare the SKSE type — which risks contamination.
   - What's unclear: Whether forward declaration alone (`class Actor;`) suffices without pulling in SKSE definitions.

# Phase 2.5: SKSE Abstraction Layer - Context

**Gathered:** 2026-03-30
**Status:** Ready for planning

<domain>
## Phase Boundary

Abstract ALL client service interactions with Skyrim/SKSE behind a set of focused bridge interfaces. After this phase, no service file in Code/client/Services/ calls SKSE or game memory directly — all game interaction flows through bridge interfaces. A recording SkyrimBridge captures all calls/returns to NDJSON during live play, and a ReplayBridge plays them back for headless automated testing.

</domain>

<decisions>
## Implementation Decisions

### Interface Granularity
- **D-01:** Multiple focused interfaces, one per logical grouping — e.g., `IActorBridge` (actor access, state queries), `IFormBridge` (form lookups, TESForm operations), `IEventBridge` (game event hooks, papyrus events), and potentially others as the groupings emerge from the actual SKSE call sites. Not a single monolithic interface.

### Bridge as Sole SKSE Gateway
- **D-02:** The bridge interfaces are the ONLY code that calls SKSE APIs or accesses game memory. No service in Code/client/Services/ may include SKSE headers or call game APIs directly. All 24 service files must be migrated — no exceptions, no deferred services.
- **D-03:** The real `SkyrimBridge` implementation is the sole file (or small set of files) that `#include`s SKSE headers and interacts with game memory. This creates a hard compilation boundary — if a service compiles without SKSE headers available, the abstraction is correct.

### Recording and Replay
- **D-04:** `SkyrimBridge` (the real implementation) instruments all calls to record call/return data to NDJSON format during live play. This produces test fixtures automatically from real gameplay sessions.
- **D-05:** `ReplayBridge` reads recorded NDJSON and replays canned responses for headless execution. A headless test binary can instantiate ReplayBridge, feed recorded data, and exercise services without Skyrim running.
- **D-06:** NDJSON format should be client-side event schema (form IDs, actor state, positions, event types) — distinct from the server-side enet NDJSON format used by `ServerReplayHarness`.

### Abstraction Scope
- **D-07:** All 24 service files that touch SKSE/game APIs are abstracted in this phase. No partial rollout, no deferred services. The full list: CharacterService (56 calls), PlayerService (26), MagicService (23), ObjectService (14), OverlayService (11), InventoryService (11), CombatService (10), ActorValueService (8), QuestService (6), MapService (6), TransportService (5), CommandService (4), WeatherService (2), DiscordService (2), PartyService (1), plus Debug service files.

### Claude's Discretion
- Injection mechanism — follow existing codebase patterns (likely World context via `entt::registry::ctx()` since services already pull dependencies from World). Pick whatever fits best with existing code.
- Exact interface split — the logical groupings (IActorBridge, IFormBridge, IEventBridge, etc.) should be determined by analyzing actual SKSE call sites during research. The principle is "one interface per logical concern," not a prescribed list.
- NDJSON schema design — field names, structure, recording granularity. Follow the pattern established by `ServerReplayHarness` where applicable.

</decisions>

## Existing Code Insights

### Reusable Assets
- `ServerReplayHarness` — Established NDJSON replay pattern for server side. Client ReplayBridge should follow same recording/replay architecture.
- `EnetRecorder` — NDJSON recording infrastructure. Client-side recording can follow same file I/O patterns.
- `entt::registry::ctx()` — Existing dependency injection pattern used throughout World. Bridge interfaces should use same mechanism.

### Established Patterns
- Services pull dependencies from `World` context via `m_world` member
- Event-driven via `entt::dispatcher` subscriptions
- No-exceptions policy (Phase 1 D-04)
- Message handler registration via opcode array

### Integration Points
- `World` class constructor — where bridge instances would be registered in context
- `Code/client/main.cpp` — where real SkyrimBridge gets created (game startup)
- Test binary entry point — where ReplayBridge gets created (headless testing)
- `Code/client/TiltedOnlinePCH.h` — precompiled header, bridge headers may need inclusion

</code_context>

<specifics>
## Specific Ideas

- The bridge creates a hard compilation boundary: if a service compiles without SKSE headers available, the abstraction is verified correct
- User has access to full SKSE source code, so identifying all call sites is straightforward
- Recording happens automatically during live play — no manual fixture creation needed
- This enables fully automated headless testing of the entire client service stack
